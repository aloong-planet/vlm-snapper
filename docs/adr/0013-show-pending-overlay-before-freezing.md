# ADR-0013: 截图触发后先显示待冻结遮罩

- 状态: 已接受（2026-10-28）

## 背景与问题

ADR-0010 要求全部可用显示器冻结完成后才建立选区遮罩。在 Apple M1 Pro 的 Retina 屏上，ScreenCaptureKit 冻结一块显示器约需 100–200 ms（进程内首次更慢），旧遮罩再在主线程新建面板并重绘整幅冻结帧，用户按下快捷键后约 160–325 ms 才看到任何反馈，并明确反馈截图“需要过一会儿才能出来”。对照 Snipaste 2.7.2 的静态逆向报告：它复用常驻全屏窗口，只抓光标所在屏后立即显示，抓屏走同步 CoreGraphics 接口；VLMSnapper 必须冻结所有显示器，而 `CGWindowListCreateImage` 与 `CGDisplayCreateImage` 自 macOS 15 SDK 起已不可用，ScreenCaptureKit 的冻结耗时压不到一帧以内。

## 备选项

1. **截图准入后立即在每块显示器上显示与冻结后外观相同的待冻结遮罩，同时冻结；冻结帧就绪后放入同一遮罩窗口，失败时撤下待冻结遮罩并恢复原状态**
2. 保持先冻结后显示，只优化冻结与绘制（缓存内容快照、复用面板、图层渲染）——否决：实测冻结本身仍需约 65–150 ms，进程内首次约 200 ms，仍是可感知的延迟。
3. 依赖 `NSWindow.sharingType = .none` 把遮罩排除在冻结帧外——否决：ScreenCaptureKit 对该属性的处理并不一致（Apple 开发者论坛中 DTS 已要求提交缺陷报告），第三方也报告了 macOS 15 起的行为变化；改用已采用的、在同一内容快照中按当前进程排除的内容过滤器。
4. 回退到 CoreGraphics 同步抓屏——否决：两个接口在 macOS 15 SDK 中均为 obsoleted，只能动态调用，随时可能被移除。
5. 常驻 ScreenCaptureKit 屏幕流以便随时取帧——否决：持续录屏会常亮系统录屏指示并持续占用资源，与 ADR-0010“选区过程不需要持续录屏”相悖。
6. 预先建好下一组遮罩面板，触发时只排序显示——暂缓：待冻结遮罩的主线程显示开销实测 4–11 ms，已低于 60 Hz 下一帧；预建需要处理显示器变化与隐藏面板的生命周期。重启条件：该开销超过一帧（16 ms）。

## 决策

选定**方案 1**。截图请求通过准入后，我们立即在每块已连接显示器上显示待冻结遮罩：与冻结后相同的暗色遮罩覆盖实时屏幕，不新增加载提示或文案；同一时刻开始冻结。冻结仍按 ADR-0010 从同一 ScreenCaptureKit 内容快照中排除 VLMSnapper 自身，因此待冻结遮罩不会进入冻结帧。

冻结帧就绪并通过几何复核后，帧作为图层内容放入原遮罩窗口，不重建窗口；没有冻结帧的显示器撤下其遮罩；之后才退下旧遮罩、旧操作栏、待替换的结果工作区与已记录的来源界面。

待冻结期间遮罩接管键鼠，包括透明的选区内部。冻结帧到达前完成的矩形拖拽保留，帧到达后按冻结帧裁切。`Esc` 或应用准备退出时退出截图，包括被替换的旧选区；为本次截图预留的结果工作区恢复可用，迟到的冻结结果丢弃。冻结失败、新遮罩无法覆盖任何显示器或请求失效时撤下待冻结遮罩，原选区遮罩与操作栏原样恢复。

本决策取代 ADR-0010 中“全部可用冻结帧完成后，应用先建立新的不透明 `.screenSaver` 级选区遮罩”的显示时序；冻结时机、裁切来源、排除自身、失败保留与资源释放等其余决定不变。

## 后果

- 正面：按下快捷键到出现选区遮罩从约 160–325 ms 降到主线程约 4–11 ms 加一次屏幕刷新，进程内首次截图同样即时；拖拽选区不再在主线程重绘整幅冻结帧。
- 正面：冻结完成前的鼠标与键盘不再落到下层应用。
- 负面：冻结帧在遮罩出现后约 100–200 ms 才替换实时画面；这段时间视频或动画仍在暗色遮罩下播放，菜单栏面板、管理中心或结果窗口等 VLMSnapper 界面在遮罩下可见，冻结帧替换后从画面中消失。
- 负面：冻结帧不含遮罩完全依赖按当前进程排除的内容过滤器；ScreenCaptureKit 的合成结果只能在签名 App 中验收。
- 中性：冻结前后选区界面外观一致，没有新的界面形态或文案。
