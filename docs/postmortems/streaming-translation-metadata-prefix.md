# 合法翻译 JSON 被流式元数据前缀误判

## 故障与复现边界

2026-09-24，安装版 0.1.0 (48) 的历史原文翻译显示“Provider 返回了不完整或无法解析的结果”。用户这一次原始响应未留存，不能证明它与复现逐字节相同。随后经授权，以合成中文多段落调用 deepseek-flash，复现了相同的 incompleteOutput → incomplete_response 路径；没有读取或上传历史正文。

## 已验证的因果链

真实响应是完整且合法的 JSON，原文、身份和布局信息均与请求一致。但是第一个片段把 `block` 放在最后，内容为 `saved`。在流式输入只收到 `s` 时，AlignedTranslationParser 将通用字符串前缀逻辑同样用于元数据，发布了 block 为 `s` 的片段。SavedTextTranslation 正确拒绝它与本地 `saved` 不一致，整次转换提前失败。

根因是解析器提前公布不完整身份，而不是最终 JSON 需要修补。临时探针保存了去掉推理字段的合成响应，离线回放稳定失败；修复后同一响应完整通过。第二次真实调用同样通过四段完整对应校验。

## 修复与安全边界

仅允许 `source` 和 `translation` 的字符串前缀参与流式快照；`id`、`block`、`kind` 必须读到完整字符串后才参与身份判断。正文仍流式显示，不等待整篇结束；后置元数据只延后该片段的首次公布。三个 Provider 共用此解析器，截图翻译和历史原文翻译同时受益。

没有放宽截断、重复身份、非法类别、缺段或原文被改写的校验；没有猜测对应关系、自动发出修复请求或修改用户模型。失败时仍保留原记录。

## 为什么此前测试没有拦住

旧逐字符乱序样本使用单字符 ID，因此收齐第一个字符就恰好等于最终身份；block 又在 source/translation 前，此时没有文本可供公布。App 集成样本则先给完整元数据，再流式发送译文，避开了元数据最后到达的形态。离线测试与预想的字段顺序相关，未覆盖真实模型这次的输出顺序。

## 防线

- AlignedTranslationTests.metadataIsNeverPublishedAsAPrefix：多字符身份/块/类别分别后置，逐 Unicode scalar 输入；每次快照均经过公开对应校验，最后断言完整原文和译文。修复前 id/block 两例准确失败。
- ProviderApplicationTests.savedExtractionConvertsThroughProductionCallback：HTTP SSE 分块在末尾 block 的 `s` 后断开，经正式应用回调直到 SQLite 查询，检查同一记录转换、元数据保留及后继图片重试。临时恢复旧解析条件时，有图/缺图两个分支都在成功提交断言失败；只撤销该变异后重测。
- 实际失败响应离线回放与一次修复后真实请求是不同证据，均保留；两个请求预算没有追加重试。签名时间戳服务首次失败发生在联网模型请求之前，不计作模型调用。
